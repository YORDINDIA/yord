# YORD India — Agent Guide

Monorepo: Shopify → Supabase migration + luxury concert-fashion e-commerce (Coldplay, Taylor Swift, Diljit Dosanjh, Linkin Park, The Weeknd).

## Layout

- `frontend/` — customer storefront (Next.js 16 App Router, React 19, TS). Deployed to Netlify, Node 20 required.
- `admin-dashboard/` — admin panel (Next.js 16, layered data/action/UI, Agnes AI + Razorpay refunds). SQL in `admin-dashboard/sql/`.
- `scripts/` — Python Shopify → Supabase migration + audit tooling. Schema in `scripts/schema.sql`, patches in `scripts/schema_patches/`.
- `packages/` — shared workspace packages (`@yord/ui` tokens/CSS, `@yord/db-types`, `@yord/auth`, `@yord/supabase-clients`) consumed via npm workspaces; both Next configs list them in `transpilePackages` because they export raw TS.
- Root `package.json` holds the Remotion video deps and the `turbo` tasks (`turbo.json`); app code lives in the two sub-apps plus `packages/`.

## Commands

Each Next.js app runs from its own dir (`frontend/` or `admin-dashboard/`):

```bash
npm run dev    # dev server (localhost:3000), 4GB heap flag is built into the script
npm run build  # production build
npm run start  # start production server
npm run lint   # ESLint (eslint-config-next)
npm run clean  # rm -rf .next
```

A root `npm install` sets up the workspaces for both apps. Tests: `npm run test` (vitest) where a `vitest.config.ts` exists — the frontend has checkout/pricing/error-model/sanitize suites, the admin has pagination/validation/sanitizer/action-state/route-coverage suites. Do not add heavier test infrastructure unasked.

Admin builds need the Supabase env vars present: every admin route is dynamic, and without `NEXT_PUBLIC_SUPABASE_URL` the build fails at prerender with "Missing NEXT_PUBLIC_SUPABASE_URL". CI supplies mock values (`.github/workflows/ci.yml`).

Python scripts (run from `scripts/`, ~5 min for venv setup first time):

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r ../requirements.txt   # requirements.txt lives at repo root
python migrate_via_rest.py --dry-run   # preview; use --execute to write
python verify_migration.py --quick     # use --full for details
python yord.py migrate --dry-run       # whole pipeline plan + env check; --execute to run
```

## Architecture

### Frontend (`frontend/src/`)
- `app/` — thin App Router routes + `error.tsx`/`loading.tsx`/`not-found.tsx` per segment; API routes (`api/` covers checkout, contact, newsletter, search, **products**); dynamic `[handle]/` routes for products/collections/artists.
- `features/` — feature slices (`catalog/`, `product/`, `artist/`, `collection/`, `cart/`, `checkout/`, `home/`, `layout/`, `ui/`, `auth/`, `support/`, `concerts/`, `blog/`). Routes fetch + render metadata; presentational/client work lives here. The one catalog grid is `features/catalog/CatalogGrid.tsx`.
- `hooks/` (`useAuth`, `useRazorpay`, `useProductsInfinite`, `useHydrated`), `providers/` (PostHog + React Query `QueryClientProvider`).
- `lib/supabase/` — three clients in `client.ts` (browser) / `server.ts` (regular, service, static) + queries in `queries.ts`. `lib/stores/` — Zustand cart/wishlist with localStorage persistence (client-only). Focused helpers: `lib/product.ts` (catalog logic + canonical `SortOption`), `lib/search.ts` (PostgREST escaping), `lib/sanitize.ts` (`sanitizeHtml`), `lib/text.ts`, `lib/errors.ts` + `lib/result.ts` (error model), `lib/catalog-url.ts` lives at `features/catalog/catalogUrl.ts`.
- Schema types come only from `@yord/db-types` (no local copy). Formatting (`cn`, `formatPrice`, `formatDate`, `truncate`, `stripHtml`) comes only from `@yord/ui`. Path alias `@/*` → `./src/*`. Design tokens live in `packages/ui/src/tokens.css`, imported at the top of `app/globals.css`.
- Server Components fetch via `queries.ts` by default; `'use client'` only for interactivity (cart, forms, modals).
- **Images:** the storefront serves Cloudflare R2 through a custom `next/image` loader (`src/lib/media-loader.ts`, wired as `images.loaderFile`) instead of the built-in optimizer, so there is no `remotePatterns` to edit. The bucket holds one web-optimized WebP variant per image (max 1600px, built on upload — AI-generated images are the one exception: PNG, see `docs/deploy.md` §5), so there is nothing to transform: the loader returns stored URLs unchanged, rewrites stored `*.r2.dev` origins to `NEXT_PUBLIC_MEDIA_BASE_URL` when that is set, and passes everything else (Shopify CDN, legacy Supabase, local files) through. Tests: `src/lib/__tests__/media-loader.test.ts`.
- **Error model:** empty → `[]`, missing row → `null` (page calls `notFound()`), failed read → throws `DatabaseError` (nearest `error.tsx`). Optional sections use `queryOrDegrade`. Never render "no results" for a failed read.
- **Unconfigured Supabase (no URL/publishable key):** reads degrade to empty so a backend-less `next build` prerenders; clients use a placeholder endpoint + warn. A *configured but unreachable* backend throws → error boundaries. CI builds with localhost mock values for these (`.github/workflows/ci.yml`), which is the supported way to build without real credentials.
- **Catalog pagination:** page 1 is SSR HTML; pages 2+ come from `GET /api/products` (zod params, 60/min IP limit) via `useInfiniteQuery`. `?sort=` navigates to fresh SSR; `?page=` syncs via `replaceState`.
- **Auto collections:** `new-arrivals` and `all` have no authored membership — `lib/data/autoCollections.ts` answers them from `products` (active, newest first, same sort vocabulary and paging as any other collection), so the header/footer links can never point at an empty or stale page. The collection row still gates the route (unpublished/deleted → 404). The admin mirrors the handle list and renders those two read-only. Their `collects` rows are ignored here and cleared by `scripts/tidy_collections.py`, so seeding them is unnecessary; they were seeded once (2026-10-02: 48 newest + all 463 active) purely as a stopgap while the deployed build still read `collects` — treat any rows found there as disposable, never as the source of truth. A collection's own `sort_order` (`newest`/`price-asc`/`price-desc`/`title`, or `manual` = the admin picker's saved order, persisted as `collects.position` by the `set_collection_products()` RPC and preserved verbatim by the id-list fetch) is its default order when the shopper passes no `?sort=`; the auto collections ignore `manual` (they have no `collects` rows to order by) and degrade to `newest`.
- **`products.published_at` is what `newest` sorts on**, and the migration left it NULL for every row (so "newest" was arbitrary). `scripts/tidy_collections.py` backfills it from `created_at`; keep it populated for new products.
- **Cart ownership:** guest carts are claimed on sign-in only after persist rehydration (`claimCartForUser`); actions selectors use `useShallow`. Gate persisted reads on `useCartHydrated`/`useWishlistHydrated` to avoid empty-flash.
- Auth: `src/proxy.ts` (Next 16's middleware) guards `/account/*` via Supabase SSR cookies; auth pages redirect logged-in users to `/account`.
- Tests: `npm run test` (vitest, `src/lib/__tests__/` + `src/**/*.test.ts`) — error-model, product/catalog-helper, search-filter, sanitize, checkout-gate, auto-collection, theme-contract, media-loader, concerts and logger suites, among others (212 tests in 19 files at the time of writing).
- **Theming (storefront): light is the default**, with Dark and System selectable from the header. `next-themes` writes `data-theme` on `<html>` pre-paint (`providers/ThemeProvider.tsx`, key `yord-storefront-theme`, namespaced because both apps serve :3000 in dev). Tokens live in `packages/ui/src/tokens.css` — `:root` is light ("Alabaster & Bronze"), `[data-theme="dark"]` is the original "Noir Luxe", values unchanged. `globals.css` maps them through `@theme inline`, which is load-bearing: without `inline` Tailwind emits `var(--color-x)` and the cascade cannot re-point it.
- **The token contract.** Components use semantic tokens only (`bg-surface-page/card/raised/inset`, `text-text-primary/secondary/muted/subtle`, `bg-accent`, `text-text-on-accent`, `border-border-default/strong`, `ring-focus-ring`). The `noir-*`/`gold-*`/`ivory-*` ramps are private to the token layer and are **not** mapped into `@theme`, so `bg-noir-950` does not compile and `theme.test.ts` fails the build on one. Four rules the tests enforce, each because breaking it fails silently: (1) every themed token must exist in *both* theme blocks, or the dark page silently renders light values; (2) `--text-subtle` is 3.04:1 and is for large/decorative text only — body copy uses `--text-muted`; (3) `--scrim`/`--text-on-media`/`--accent-on-media` are theme-invariant because the home hero is dark in *both* themes, so anything over a photo or video uses them and never flips; (4) artist brand colours are theme-invariant and bright, so a label on one uses `--text-on-brand` (dark ink in both themes) rather than the flipping `--text-on-accent`, and artist colour is never used as text on a page surface (a brand yellow is ~1.6:1 on light — use `--accent`). Light mode uses bronze rather than gold as the accent because the gold ramp only reaches ~3.9:1 on the light page; shadows invert from black-blur to light-lift. `manifest.ts` splash colours are light because a standalone window paints before any CSS loads.
- Stack: Supabase (Postgres + Auth), Razorpay payments, Tailwind 4 with the token system above, PostHog analytics, framer-motion.

### Admin (`admin-dashboard/src/`)
- **Layered, and the layering is the rule:** `lib/data/*` (all reads) → `server/actions/*` (all writes) → `app/(admin)/*` (thin routes) → `components/*` (rendering). No page or component may call `.from()` directly, and no component may import a Supabase client. Reads go through an entity module; writes go through an action.
- **Reads — `lib/data/`** (one module per entity: products, orders, collections, blogs, customers, inventory, discounts, media, settings, analytics; `client.ts` holds the shared helpers). `client.ts` marks the module `server-only`. Three outcomes are kept distinct, matching the frontend: empty → `[]`, missing row → `null` (page calls `notFound()`), failed read → throws `DatabaseError` → nearest `error.tsx`. **Never render "no results" for a failed read.** All list helpers take `{ q, page, pageSize }` and return `{ rows, count, page, pageSize }`; no list query may use a bare `.limit()`.
- **Writes — `server/actions/`** (products, collections, blogs, orders, inventory, discounts, settings, media, ai). Every action has the signature `(prev: ActionState, formData: FormData) => Promise<ActionState>` and runs inside `withAdmin()` in `_shared.ts`, which only authenticates (via `requireAdminAction()`) and converts any throw into a form-level error. Parsing, writing, and auditing happen in each action body around it: parse with `parseForm()` (zod schema, shared with the client), write via the service client, record with `audit()`. **No action returns `undefined`** — a silent success is the bug this structure exists to prevent. `audit()` is never fatal: a failed audit logs loudly and does not invalidate a committed write.
- **`ActionState`** (`lib/action-state.ts`) is the single mutation return shape: `status`, `message`, `data`, `formError`, `fieldErrors`. `useActionForm` / `ActionField` / `FormError` (`components/forms/`) give every form the same three feedback channels: banner, per-field message, and toast. New forms use these rather than raw `useActionState`.
- **Validation** is `lib/validation.ts` only (zod), shared by client and server. HTML written by an admin or a model (`body_html`, `summary_html`) is sanitized by `lib/utils/sanitize.ts` on the way in — it is rendered with `dangerouslySetInnerHTML` downstream.
- **Shared list UI** in `components/data/`: `DataTable` (always wraps in `.table-wrap`; `hide-mobile`/`hide-tablet` drop secondary columns at 768px/1024px), `Pagination`, `FilterBar`, `SearchInput`, `BulkActions`, `TableSkeleton`. A new list page composes these instead of writing a `<table>`; each `DataTable` gets `emptyTitle`/`emptyHint` so "no results" is never a bare empty table.
- **UI system:** every page starts with `PageHeader`, and layout uses `.dash-grid`/`.col-*`, `.layout-split`, `.side-rail` from `globals.css` plus the primitives in `components/ui/` (`StatCard`, `TrendPill`, `Avatar`, `Thumb`, `Tabs`, `ProgressBar`, `Tooltip`, `EmptyState`, `StatusBadge`, `ConfirmModal`) and the Recharts kit in `components/charts/` (`ChartCard`, `AreaTrend`, `Bars`, `Donut`, `Sparkline` — client components taking serializable props; pass the same `height` to a `ChartCard` and its chart). All colour comes from the tone triplets (`--tone-*`/`--tone-*-soft`/`--tone-*-line`) and the per-section accent `--accent-local`, never raw hex. `src/lib/sections.ts` is the single source for nav sections, breadcrumbs and accents; `docs/06-ui-system.md` documents the whole system. The motion layer is ReactBits (MIT, vendored under `components/reactbits/`) wrapped so every colour resolves a token through `useReactBitsColors()` and every animation collapses under `prefers-reduced-motion` via the hydration-safe `useReducedMotion()` in `lib/reduced-motion.ts` — new animation goes through those wrappers, not raw motion/gsap.
- **Route states:** `(admin)/error.tsx`, `loading.tsx`, `not-found.tsx` apply to every admin route. All admin routes are dynamic by design — they require a live session, so never make one statically prerenderable.
- **Providers** live in the root layout: `ToastProvider` (context, not `window.dispatchEvent`). The admin app has no React Query; client fetches go through `postJson` (`lib/utils/post-json.ts`).
- API routes call `requireAdmin()` (secret-key client) and validate with the shared schemas. Page-level gates (`middleware.ts`, `(admin)/layout.tsx`) read `admin_users` with the publishable client, so `sql/003_admin_rls.sql` must keep the `admin_users_self_read` policy or every admin sees "Access denied". Admin-only reads/writes (settings page) use the service client.
- `middleware.ts` has two route lists — `ADMIN_ROUTE_PREFIXES` (read at request time) and the `config.matcher` (Next parses it statically, so it cannot spread the constant). `src/lib/__tests__/routes.test.ts` asserts they agree with the real `src/app/(admin)/*` tree; keep all three in step when adding a page.
- Refunds reserve a row via `reserve_refund()` in `supabase/migrations/002_refund_idempotency.sql` before calling Razorpay, and support partial refunds up to the transaction total. The money path stays in `POST /api/refunds`; the UI (`orders/refund-panel.tsx`) pre-validates with the shared `refundSchema` for fast feedback, then posts through `postJson`. The route hand-validates its payload and is the boundary.
- Products/collections/discounts use BIGINT ids via `admin_next_id` (see `sql/001_admin_tables.sql`, `002_admin_next_id.sql`); `getNextId` memoizes one service client. Multi-row writes go through the RPCs in `sql/004_atomic_writes.sql` (`set_collection_products`, `set_product_variants`, `set_cover_image`) so a mid-loop failure cannot leave a partial set; analytics aggregate in SQL (`revenue_by_day`, `top_products_by_units`). The RPCs signal expected outcomes by raising (`IMAGE_NOT_FOUND`, `COLLECTION_NOT_FOUND`, `INVALID_VARIANT_ROWS`); actions map those to specific copy and keep a generic "nothing was changed" message for everything else. `updateVariantsAction` verifies every submitted variant id belongs to the submitted product, because the RPC is id-keyed and cannot check that itself.
- Forms that render an HTML checkbox must use `checkboxSchema`, not `z.coerce.boolean()`. An unchecked box is absent from `FormData` entirely, and `z.coerce.boolean()` turns the string `"false"` into `true`, so `z.coerce.boolean()` fails on the empty case and inverts the "on"/"off" case. New products have no status control and always start as `draft` via the schema default.
- **Collections:** membership is edited with the searchable picker (`components/collections/ProductPicker.tsx`), which still submits the hidden `product_ids` field so the atomic `set_collection_products()` RPC is unchanged. `lib/collection-rules.ts` compiles a `smart_collection_rules` row into a PostgREST filter (pure, unit-tested) — values are double-quoted inside `or=(...)`, the only form PostgREST accepts (backslash escaping answered `PGRST100` for a comma and silently returned zero rows for a parenthesis), and rules whose column/relation it does not implement are reported to the UI rather than dropped silently — and `resolveSmartRuleMatches` turns it into products; the storefront reads `collects`, so a rule only takes effect through **Apply now**, and an empty match is refused rather than wiping the list. `new-arrivals`/`all` are computed on the storefront (`lib/data/autoCollections.ts`) — the admin renders them read-only from the mirrored handle list in `lib/constants.ts`. Publishing stamps `published_at` once (later saves never rewrite it) and is refused for an empty collection — custom *or* smart — in the picker UI and in the action. The two auto handles survive a save: their disabled `published`/`collection_type` controls submit nothing, so the action keeps those fields (plus `published_at`/`disjunctive`) from the stored row and skips the `collects` replace. `sort_order` becomes the collection's default storefront order when no `?sort=` is passed, and `manual` persists the picker's saved order as `collects.position` through the atomic RPC (admin SQL `005`), which the storefront preserves verbatim. `listCollections` filters/sorts in memory because product counts are computed from `collects`; it pages after that, so its `count` is the filtered total — it scans a 2000-collection window and returns `truncated` so the page can warn instead of dropping rows silently.
- HTML from a model is sanitized at render as well as on save: `sanitizeHtml` is dependency-free and safe in the client, and the AI studio previews render through it. Sanitizing only in the save action leaves the preview as a script-execution surface on the admin origin.
- Client `error.tsx` cannot `instanceof DatabaseError` — Next serializes only `message`/`digest` across the boundary — so `DatabaseError` prefixes its message with `Could not read <entity>:` and the boundary matches on that. Keep the format and the regex together.
- The focus ring is `--focus-ring`, set per theme. The saffron accent is ~10:1 on the dark panel but only ~1.6:1 on the light one, below the 3:1 non-text minimum; a single hardcoded accent would leave light-theme keyboard users with no visible focus.
- `SearchInput` resyncs to the URL by adjusting state during render, keyed on the last observed `q`. A `key` on its own returned element does nothing (keys only matter among siblings), and the `useEffect(() => setState(prop))` form is both a lint error and a fight with the debounce.
- Routes with two paginated tables (blogs + articles, product + article media) pass a distinct `pageParam` to each `Pagination`, so paging one table does not move the other.
- Inventory search resolves product-name matches in a second query and ORs the ids in. The two-query shape exists because the obvious one-liner silently dropped the product-name half: PostgREST cannot filter on an embedded resource's column without embedding it, and embedding would drop the `product_variants` filter (inner join). The id list is bounded (500) and an empty match falls back to the variant-title half alone, since PostgREST rejects an empty `in ()`.
- Schema types come only from `@yord/db-types` — the local `src/types/database.ts` copy is deleted.
- AI endpoints use Agnes AI (Chat Completions + `POST /v1/images/generations` image edits, `AGNES_AI_API_KEY` required). AI writes go through the same audited actions as the UI: `AiBlogStudio` calls `saveAiDraftAction` directly, and `/api/ai/listing/apply` delegates to its action. Refunds run through Razorpay server-side.
- Tests: `npm run test` (vitest, `src/lib/__tests__/` and `src/server/actions/__tests__/`) — pagination/query-string, shared schemas (including checkbox regressions), `refundSchema` + partial-refund classification, sanitizer, `ActionState`, error-boundary message contract, Agnes request shapes, collection rules/publishing/list, the collection action driven through a stubbed admin boundary, and route coverage, among others (242 tests in 23 files at the time of writing). Tests import the real module; a test that re-implements the code as a local copy cannot fail when the code does, and a test that passes an extra field the form does not render will not catch a schema/form mismatch.

### Scripts (`scripts/`)
- `utils/` shared layer: `shopify.py` (ShopifyClient, auto-pagination + retry), `supabase_helpers.py` (client + `batch_upsert`), `cli.py` (the standard `--dry-run`/`--execute`/`--batch-size`/`--verbose` flags + `resolve_execute`), `config.py` (env resolution — `resolve_supabase_url`/`resolve_supabase_secret_key`/`resolve_r2_*` — and `ARTIST_COLLECTIONS`), `logging_config.py`.
- Fresh-migration order: apply `schema.sql` → `migrate_via_rest.py --execute` → `migrate_media.py` → `migrate_blogs.py` → `populate_collections.py --mode=keyword --execute` → `verify_migration.py --full` → `optimize_images.py` (no `--execute` flag; it runs on invoke).
- `tidy_collections.py` (dry-run by default, `--execute` to write, `--no-delete` to merge without deleting; run it from `scripts/` — it reads the root `.env` from either directory but writes its snapshot to the cwd) is the post-migration cleanup: it backfills `products.published_at` from `created_at` (the migration leaves it NULL, and `newest` sorting reads it), rebuilds the keyword-driven collections from `TITLE`/`TAGS`/`PRODUCT_TYPE` rules (`any` = OR within the list, `every` = AND across groups, OR inside a group; a rule that matches zero products is refused and the collection left untouched), merges near-duplicate handles into a canonical one and deletes the duplicates, unpublishes collections that end up with no products, and assigns every *active* product to at least one collection. Curated collections (`premium-store`, `tshirts-adt`, festival lineups) are rule-free by design — do not "fix" them with a keyword rule; a rule-free collection's membership is only ever added to (a merge/seed union), never replaced, though it can still be unpublished as empty. **Rules are authoritative, so a run is not necessarily a no-op**: each rule collection is replaced by what the rule matches today, which drops anything that got in by hand or through an earlier merge — read the dry run's `MEMBERSHIP DIFF` + `REVIEW` block before passing `--execute`. Curated exceptions live in `PINNED_MEMBERS` (unioned into the desired set after the rules run, reported in NOTES, refused with a non-zero exit if the product or collection disappears); `rainbow-reflector-coldplay-single-side-print` pins product `8190803706033` because the rule alone matches only 19 of its 20 members. It exits non-zero when a rule matches nothing or a merge/seed target is missing, so a cron/CI wrapper sees a real failure.
- **`tidy_collections.py` rollback.** `--execute` writes `collection_tidy_snapshot-<timestamp>.json` to the cwd before any write (one file per run, never overwritten): the pre-run `collections` rows with every column the script reads — `id, title, handle, published, image_src, collection_type, body_html, sort_order, published_at, image_alt, published_scope, template_suffix, disjunctive, updated_at` — plus every `collects` row and each product's `published_at`. It is the only copy of a deleted duplicate, because deleting a collection cascades to its `collects` rows. Undo by hand: re-insert the collection row and its `collects` rows from the snapshot (there is no automatic restore). Since `admin-dashboard/sql/005_positional_collection_products.sql`, `set_collection_products()` numbers `collects.position` by the submitted array's order (the 004 body numbered it by product id); the tidy script submits ids in product-id order, so a rebuild still ends up product-id-ordered, and the storefront reads `position` only for a collection whose `sort_order` is `manual`. Older snapshots (before the column list widened) hold only `id, title, handle, published, image_src, collection_type`, and the first two runs both wrote the un-stamped `collection_tidy_snapshot.json`, so run 2 overwrote run 1: the 11 collections run 1 deleted — `best-sellers`, `accessories-1`, `bands`, `magnet`, `magnets`, `bands-magnets`, `magnets-and-bands`, `lollapalooza`, `trending`, `frontpage`, `yoyohoneysingh` — are **not** recoverable from a snapshot (their membership lived on in the canonical collections and still does). The script never writes `image_src`: a merge moves membership, not covers, and it says so in the report.
- `generate_collection_covers.py` (dry-run by default, `--execute` to write; `--only <handle>`, `--force` to regenerate covered collections, `--qa-only --qa-dir <dir>` to re-gate delivered files) regenerates collection covers with Agnes AI: it writes `storage_image_url` (R2 `collections/<handle>.webp`), NULLs `image_src`, and sets `image_alt` (`"<Title> — YORD India"`), keeping a resumable checkpoint. Every generation must pass the numeric contrast gate (p75/p99/>120%/centre-sd constants in the script); never loosen the gate for a dark subject — add a pale/ivory anchor object to the prompt instead. Covers are **subject-first** (2026-10-03 owner direction): the 19 artist/cricketer/character collections depict their figure via `REFERENCE_IMAGES` (R2 `collections/refs/`, built from the local artist hero portraits plus Wikimedia press photos and product prints), which switches the call to Agnes's image-edit mode (`extra_body.image`) and prepends an identity clause — the face must match the reference photograph. Expect iteration: AI text migrates to the nearest prop (amps, bats, wristbands, cap fronts), so the ban is repeated per object and some props (bats, drum kits) are best removed from the scene entirely. Never put a bare celebrity name in a prompt — describe the look and let the reference carry the identity; flat-cartoon subjects use the theme's `raw_prompt` escape hatch.
- Scripts write checkpoints (`*_checkpoint.json`, safe to delete for restart) and error logs (`media_migration_errors.json`, `optimization_errors.json`). `migrate_via_rest.py` only marks an entity checkpointed when the run logged zero record errors, and stores the `{supabase, store}` source it migrated from so `--resume` refuses a checkpoint belonging to a different source.

### Analytics & monitoring (both apps)
- Every integration is env-gated: an unset key disables it, so local dev and CI stay silent.
- **Behavioral events (first-party, storefront → admin)**: the storefront collector `frontend/src/lib/analytics/` queues page/product views, searches, cart and wishlist actions (and checkout outcomes) and batches them to `frontend/src/app/api/analytics/events` (shared zod schema in `lib/analytics/eventsSchema.ts`, IP rate limit, service client). Rows land in `analytics_events` (`supabase/migrations/010_analytics_events.sql` — RLS on, no policies, service-role only) and the admin reads rollups through `lib/data/traffic.ts` → the `analytics_*` RPCs, shown in the analytics page's engagement section. `order_completed` is written server-side by `verify-payment` (idempotent replays return before it) with an optional uuid-shaped `analyticsSid` from the client. No PII: `sid` is a random per-browser uuid in localStorage, never joined to `customers`. PostHog stays untouched — behavioral analytics are deliberately first-party only. Purge old rows with `purge_analytics_events(p_before)` (service role); without it the table grows unbounded.
- **PostHog** (both apps): pageviews via `providers/PostHogProvider.tsx` + `PostHogPageView.tsx`; the storefront also records sessions, the admin does not (`NEXT_PUBLIC_POSTHOG_KEY`/`_HOST`).
- **GA4** (storefront only): `<GoogleAnalytics>` from `@next/third-parties` in `src/app/layout.tsx`, rendered only when `NEXT_PUBLIC_GA_MEASUREMENT_ID` is set. GA4's enhanced measurement captures SPA route changes — there is no manual pageview call.
- **Search Console** (storefront only): `metadata.verification.google` from `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`; `robots.ts`/`sitemap.ts` already expose the sitemap GSC needs.
- **Sentry** (both apps, free tier = errors only): `src/instrumentation.ts` (runtime register + `onRequestError`, which is what captures server-render errors) and `src/instrumentation-client.ts`, sharing `src/sentry-options.ts`; `next.config.ts` is wrapped in `withSentryConfig`. Keep it free: `tracesSampleRate: 0` and no replay/profiling/log integration is ever installed. `enabled` needs a DSN **and** `NODE_ENV=production`, so dev never spends quota. Source maps upload only when `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN` are in the build env — without them the build is unchanged (CI relies on this). Client boundaries report through `useReportError` (admin: inline in `(admin)/error.tsx`), and `global-error.tsx` catches root-layout failures.

## Environment

- One env file for the repo: copy root `.env.example` to root `.env` (gitignored, never commit). No per-app `.env*` files; both Next apps preload it via `dotenv -e ../.env --no-expand` in their `dev`/`build`/`start` scripts (a missing file is ignored, so CI/Netlify env vars keep working and always win over file values).
- Frontend needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, server-only `SUPABASE_SECRET_KEY`, `RAZORPAY_KEY_ID/SECRET` + `NEXT_PUBLIC_RAZORPAY_KEY_ID`, `NEXT_PUBLIC_APP_URL/NAME`, `NEXT_PUBLIC_POSTHOG_KEY/HOST`, `NEXT_PUBLIC_GA_MEASUREMENT_ID`, `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`, `NEXT_PUBLIC_SENTRY_DSN` (+ build-only `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN`).
- Admin needs the same Supabase/Razorpay/PostHog keys + the server-only `R2_*` set (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_BASE_URL`; optional `R2_ENDPOINT` / `R2_JURISDICTION`) + `AGNES_AI_API_KEY` (+ `AGNES_TEXT_MODEL`, `AGNES_IMAGE_MODEL`, optional `AGNES_BASE_URL`) + `NEXT_PUBLIC_SENTRY_DSN`.
- Scripts read `SUPABASE_URL`, falling back to `NEXT_PUBLIC_SUPABASE_URL` (same project) via `utils/config.py::resolve_supabase_url`, plus `SUPABASE_SECRET_KEY` (via `utils/config.py::resolve_supabase_secret_key`), `SHOPIFY_STORE_NAME`, `SHOPIFY_ADMIN_API_ACCESS_TOKEN`, and the `R2_*` set (media uploads). Direct-DB work (`psql`) uses `DATABASE_URL` or the `SUPABASE_DB_*` vars.
- DB migrations live in `supabase/migrations/` (apply in numeric order; each file documents its pre-flight checks). Admin SQL stays in `admin-dashboard/sql/`.
- Deploying both apps (which env var goes on which Netlify site, database order, R2 sizing, verification and rollback): `docs/deploy.md`. Verify R2 credentials with `python scripts/verify_r2.py --execute`. `CLOUDFLARE_*` and `SUPABASE_ACCESS_TOKEN` are management keys for CLI/API tooling only — no app code reads them (the Cloudflare hosting move is planned, not live).
